# コードコメント

`何をしているか` はコードの構造で説明する。コメントでは、将来の人間とエージェントに `なぜそうしたか`、`なぜそうしなかったか`、`何が成り立ち続けねばならないか`、`ここで過去に何が起きたか` を伝える。

## 基本ルール

次の順番で考える。

```text
1. 意図が自明になるまで、リネーム・抽出・並べ替え・削除を行う
2. コードに載せられない文脈が残ったときだけコメントを足す
3. 最短で役に立つコメントを、対象コードのできるだけ近くに置く
4. 短く、局所的で、陳腐化しにくい形に保つ
```

良いコメントは誤った編集を減らす。優れたコメントは、人間とエージェントが過去の失敗を繰り返すのを止める。

## コメントの判定テスト

コメントを書く前に、次を自問する。

```text
コードを明確にすればこのコメントは不要になるか?
  はい   -> まずリファクタする
  いいえ -> 足りない文脈をコメントにする

このコメントは、ちょっとしたリファクタの後も真のままか?
  いいえ -> 詳細をコードへ移すか削除する
  はい   -> 残す

このコメントは、コードには書けないことを読み手に伝えているか?
  いいえ -> 削除する
  はい   -> 残す
```

## 何をコメントするか

次のどれかを捉えているコメントは、書くだけの価値がある。

### 意図

このコードが存在する理由。

```ts
// パートナーごとのペイロードはここで正規化する。以降のパイプラインは
// 内部フィールド名だけを前提にでき、パートナー固有の分岐を持たずに済む。
```

### 制約

プロダクト・法務・プロトコル・プラットフォームの制限により、コードが従わねばならないルール。

```ts
// カードブランド名は PCI 監査エクスポート用に原文のまま保持する。
// 他の場所のプロダクト文言では親しみやすいラベルを使うが、このファイルでは使わない。
```

### 不変条件

将来の変更をまたいで真であり続けねばならない性質。

```ts
// INVARIANT: キャッシュキーには必ず tenantId を含める。
// テナント間の衝突はキャッシュミスでは済まず、データ漏洩になる。
```

### トレードオフ

一見単純な実装より、分かりにくい実装を選んだ理由。

```ts
// ロック競合を減らすため、書き込みは 250ms ごとにバッチ化している。
// 即時書き込みのほうが単純に見えたが、本番で p95 レイテンシが倍になった。
```

### 経緯

将来の編集者が知っておくべき、過去に起きたこと。

```ts
// リトライ間隔の上限は 5s のままにする。
// バックオフを長くしたところ、2024-11-18 のインシデントで決済セッションが期限切れになった。
```

### 警告

何を「単純化」してはいけないか、そしてその理由。

```ts
// これを 1 回の upsert にまとめないこと。
// 重複した webhook が順不同で届きうるため、2 段階の書き込みは意図的なもの。
```

### 参照

詳しい経緯がどこにあるか。

```ts
// CSV のエスケープは RFC 4180 に準拠し、Excel 向けのクォート例外を加えている。
```

## 何をコメントしないか

コードに書くべきことをコメントにしない。

悪い例:

```ts
// リトライ回数をインクリメント
retryCount += 1

// id でユーザーを取得
const user = await getUserById(userId)
```

良い例:

```ts
retryCount += 1
const user = await getUserById(userId)
```

悪い例:

```ts
// リクエストを組み立てる
const req = buildPaymentRequest(order)
```

良い例:

```ts
const paymentRequest = buildPaymentRequest(order)
```

弱い名前をまともな日本語へ言い換えているだけのコメントなら、直すべきは名前のほう。

## 3 種類の読み手に向けて書く

情報量の多いコメントは、次の 3 者すべての役に立つべきだ。

1. ファイルをざっと眺めている未来の自分
2. 当時の意思決定の文脈を持たないチームメイト
3. 手元の情報だけを根拠に編集を提案するコーディングエージェント

そのためには、

- 曖昧な指示語より、具体的な名詞を使う
- 壊れる対象を名指しする
- 好みではなく、結果を述べる
- issue やインシデントの ID があれば書く
- コメントは局所的かつ陳腐化しにくく保つ

## インラインコメントのテンプレート

以下をそのまま使う。角括弧は具体的な事実に置き換える。

### 判断コメント

```ts
// [制約/トレードオフ] のため [採用した方法] を使う。
// [代替案] のほうが単純に見えたが [ケース] で破綻した。[issue/インシデント] 参照。
```

例:

```ts
// 優先度が同じ請求明細はアップロード順を保つ必要があるため、安定ソートを使う。
// ハッシュバケットのほうが単純に見えたが、エクスポートの合計値が変わった。issue #214 参照。
```

### 不変条件コメント

```ts
// INVARIANT: [真であり続けねばならない性質]。
// これが崩れると [悪い結果]。
```

例:

```ts
// INVARIANT: 監査イベントには、システム起因の操作であっても必ず actorId を含める。
// これが崩れると、バックフィルとインシデントレビューで因果関係を追えなくなる。
```

### 互換性コメント

```ts
// [ブラウザ/ベンダー/レガシーシステム] の互換性のため [不自然なコード] を残す。
// [条件] を満たしてから削除すること。
```

例:

```ts
// 銀行取込ツールのために改行コードは CRLF のままにする。
// 全リージョンでパーサ v3 が稼働していると財務が確認してから削除すること。
```

### インシデントの痕跡

```ts
// [インシデント/バグ] を受けて追加。
// [トリガー] のときの [障害モード] を防いでいる。
```

例:

```ts
// INC-482 を受けて追加。
// 配送業者の webhook がリトライされたときの、配送の二重作成を防いでいる。
```

### 一時対応コメント

```ts
// TEMP: [暫定対応]。
// 「そのうち」ではなく [具体的な出来事/バージョン/期日と担当] の後に削除すること。
```

例:

```ts
// TEMP: SVG アップロードでは画像最適化をスキップする。
// `media-service` 2.4 のリリースとバックフィルジョブの完了後に削除すること。
```

### 自明でない入出力例のコメント

```ts
// 例: [入力] -> [出力]。
// [意外なルール] のため、これが重要になる。
```

例:

```ts
// 例: " ACME-01 " -> "acme-01"。
// 上流ではパートナー ID が大文字小文字を区別しない一方、空白は意味を持つため、これが重要になる。
```

## docstring と API コメント

docstring には、契約・副作用・落とし穴を書く。実装を言い直さない。

悪い例:

```py
def sync_users():
    """API からユーザーを同期する。"""
```

良い例:

```py
def sync_users():
    """課金 API からアクティブユーザーを取得し、ローカルのレコードを upsert する。

    副作用:
    - `users` と `subscriptions` に書き込む
    - `user_synced` イベントを発行する

    リトライは安全。同一アカウントに対する並行実行は安全ではない。
    """
```

境界が重要な場面では、次の構成を優先する。

```text
何を保証するか
何を変更し、何を発行するか
呼び出し側が何を用意する必要があるか
どんなときに安全でない、あるいは高コストか
```

## アンチパターン

### 実況

```ts
// items をループする
for (const item of items) {
```

コードがすでにそう言っている。

### 名前の言い換え

```ts
// ユーザーのメールアドレス
const eml = user.email
```

`eml` をリネームするか、コメントを消す。

### 曖昧な意図

```ts
// エッジケースを処理
```

どのエッジケースで、どうなるのかを書く。

### 嘘の一時対応

```ts
// TEMP: あとで消す
```

これは永遠に消えない。いつ、何の後に、必要なら誰が消すのかを書く。

### 由来不明の経緯

```ts
// 変なバグの修正
```

どのバグか。どんな条件で起きるか。消すと何が壊れるか。

### コメントの陳腐化

```ts
// createdAt の昇順でソートしたリストを返す
return users.sort((a, b) => b.createdAt - a.createdAt)
```

古びたコメントは、コメントがないより悪い。

### 長文コメント

5 行の前置きに要点を埋もれさせない。ルールか判断を先頭に置き、必要なら文脈を 1 文だけ足す。

## レビューチェックリスト

コメントを残す前に、次をすべて確認する。

```text
[] コードがすでに同じことを言っていないか?
[] 理由・制約・不変条件・トレードオフ・経緯・警告のどれかを説明しているか?
[] 何が壊れるのか、何が重要なのかを具体的に書いているか?
[] 通常のリファクタを経ても生き残りそうか?
[] 局所的なコメントだけで十分なら、余分な詳細を削れないか?
[] issue・インシデント・RFC 由来の判断なら、その参照を入れたか?
[] 賢いエージェントが誤った「掃除」をするのを、このコメントは止められるか?
```

最後の問いの答えが「いいえ」なら、そのコメントは割に合っていないかもしれない。

## 編集時のワークフロー

コードを変更するときは、

```text
1. 今回の変更で古くなったコメントを削除する
2. 対象範囲が変わったコメントを書き直す
3. 新しいコードが理由あって「不自然」に見えるなら、短い判断コメントを足す
4. 見つけたときより、コメントが少なく良い状態でファイルを離れる
```

## 既定のスタイル

- 短い文で書く
- 判断か警告を先頭に置く
- システム・フィールド・インシデント・ドキュメントを具体的に名指しする
- ぼかした言い回しより `... のため ... しないこと` を使う
- 弱いコメント 3 つより、強いコメント 1 つ
- 冗談、埋め草、他人には復元できない私的な文脈を避ける

目的はコメントを増やすことではない。将来の読み手と将来のエージェントに、より良い根拠を残すことだ。
